## N2 residual and enforceable release safeguard

**Release status: OPEN until the control is recorded and exercised.** R12's two rereads catch state visible in the observing context. The browser does not provide a shared lock between localStorage and IndexedDB across agent clusters. The HTML Standard warns against assuming a lock for localStorage, and storage events are queued. This limits cross-context ordering even when an app uses synchronous reads. E1 is an account comparison defect. E2 is transaction/result inconsistency. E3 uses a stale observation in the same process. Browser visibility does not explain those witnesses. [HTML Web Storage](https://html.spec.whatwg.org/multipage/webstorage.html#the-localstorage-attribute)

**Producers and exposure.** R1 d09449b writes account-scoped v2, R2 db8607e writes Q3 and can migrate v2 to Q3, and R3 b323d2a writes Q4 and can migrate earlier formats. R4–R7 exemplars migrate and remove retired entries while writing IndexedDB. Treat those builds as uncertified same-origin peers even though they are not the three legacy formats' producers. R8 and later retire that migration. The public pre-REL-04 build writes a different, unowned queue outside this N2 input. There are no affected keys in the checked main history, public tags, known rollback or released web trees. The live Vercel alias now resolves to a39f398, which contains none of the affected keys. The Vercel inventory contains READY deployments of R1, R2 and R3 as Preview, and prior routing evidence proves the rolling branch alias served the writer. At least one protected origin genuinely had a writer. A private build or a sideloaded native shell pointed to that origin retains the same capability, although no complete private distribution or installed-client inventory was available. [Historical writer](https://github.com/ste277/aura-updated/commit/d09449b655d21c213f8bbb29cf90f5bdc71c208e) [Public releases](https://github.com/ste277/aura-updated/releases)

**Persistence.** In Chromium, an open R1 page wrote after the same loopback origin stopped serving R1. A new page on that origin saw the write. After a full browser restart, the historical worker served an explicitly seeded cached R1 navigation offline, and the reopened page produced a second write. The old worker supplies the page and has no Window localStorage access of its own. The seed tests a retained-response condition and does not assert that deployed workers automatically cached that response. A distinct origin on the same profile saw neither write, before or after restart. An alias update, pointer change, logout, or plan to close tabs cannot guarantee writer exclusion for a reused origin. [Service Worker specification](https://w3c.github.io/ServiceWorker/#service-worker-global-scope) [Storage keys](https://storage.spec.whatwg.org/#storage-keys)

**Smallest practical control.** Keep a release-origin and rollback-commit allowlist that excludes every affected legacy writer or migrator. Use the verified writer-free Production origin for public release only if that lineage remains intact and the configured native origin matches. For a Preview, internal or sideloaded population that may have loaded an affected build, serve the R12-or-later program from a clean, dedicated origin that never serves an affected build, including during rollback. Keep the old origin isolated for any required account-scoped recovery, with no automatic raw-state transfer. Approve upgrade and every rollback candidate against the same allowlist. A genuinely new origin bounds the risk even if a user keeps old tabs, worker caches or a restored WebView profile.

**Acceptance test.** In a disposable profile for each supported browser/WebView class, run the latest actual legacy writer for each exercised format on the historic endpoint. Leave a tab or WebView open, preserve an offline worker-controlled document, and restart or restore that profile. Use a release candidate and the actual approved rollback at the proposed release origin. Demonstrate a successful legacy write on the old origin as a control, zero legacy mutations in the release origin during upgrade and rollback, zero cross-origin retired entries, and correct account/request/row attribution for one healthy online write and one replay. On a synthetic affected origin, confirm that a *visible* contradictory entry prevents the matching send. Record served SHA, native origin and rollback SHA. Fail acceptance if the planned rollback exposes a legacy writer or if the release origin's history cannot be established. If same-origin coexistence with unmodified writers remains mandatory, N2 stays OPEN. A fingerprint seal that still depends on seeing new localStorage writes cannot close that gap. The smallest enforceable structural alternative is to isolate the supported outbox on a clean origin and use an explicit, account-scoped recovery path from the retired origin. For cooperative clients, any future shared quarantine authority would need to participate in the same IndexedDB transaction as the claim.
