# 39256 — Android operation identity and reconciliation architecture reassessment

Consolidate the client operation contract around the existing account-bound outbox, claim and decision transactions. A single operation must keep its request ID until there is evidence of success, definitive failure or durable discard. The current authenticated API and database can prove success for the supported activity payload. Keep the R14 NO-GO and ticket 39243 open pending implementation and independent verification.

## Authoritative success

- Direct and replay use one decoder for the authenticated, same-origin habit-logs route. Reject redirects. Require a route-supported success status, JSON media type and a validated row with a nonempty server record ID, the expected account, the exact request ID and matching persisted intent. Accept an authenticated GET row only after those same row checks and while the account lease is current. Unsupported responses, malformed bodies, mismatched rows and stale account results leave the operation unresolved. Preserve the claim and retry rules.
- Compare a normalized projection of the server-persisted intent. Match the trimmed title, validated optional activity reference, explicit timestamp as an instant, normalized notes, bounded duration including zero, source and significance. Exclude server-derived fields such as `activeWindow` and `logMinuteOfDay`. Separately retain the full canonical dispatch payload for local retry and claim equality. If a legacy record lacks enough comparable intent, preserve it as unresolved.
- Persist a versioned receipt with the account, request ID, canonical payload binding and validated server record ID. Validate the marker key and value against the operation and the receipt before returning success. Old bare accepted markers can be upgraded from positive authoritative evidence. Contradictory or incomplete markers supply neither success nor destructive cleanup authority. A correctly bound existing discard can continue to fence sends even when the discarded payload was damaged.
- The existing route returns the existing row or the newly inserted row. PostgreSQL guarantees uniqueness by account and ID. The route can return the existing row before comparing incoming fields, so the client must compare persisted intent. The collection GET spans 400 days and can supply positive matching evidence. Absence from any list, including a fresh list, is inconclusive. Where authorization and durable fences permit it, replaying the exact same ID and payload can resolve an ambiguous send through the existing idempotent POST. A read-only exact-ID lookup would be the smallest optional addition if a product requirement calls for historical confirmation without any possible write. It can reuse the authenticated lookup without a schema change. A server-stored, versioned intent fingerprint would become necessary only if future correctness depends on fields absent from the returned and persisted row. Neither addition is required for the demonstrated failures. ## Identity continuity and outcome transitions

Mint once on an explicit new operation. Capture an immutable account, request ID and canonical payload. Anchor that handle in the existing IndexedDB transaction before the first fetch, with enough local context to reattach the initiating UI after remount or restart. Carry the same handle through direct submission, replay, settlement, Home and Timeline. Keep it recoverable through cross-tab settlement by retaining the receipt or unresolved record. A second tab’s notification should trigger an account-scoped reread. An older list response can update displayed history, but cannot release an unresolved handle. Apply results only to the current account and relevant operation.

“Retry” resumes the original handle and payload. “Start now” for a genuine separate operation can mint a new ID after the earlier action is resolved. Separate operations may have identical payloads. If a write acknowledgement, store read or recovery fails, retain the in-memory handle where available and retry the authoritative lookup. After reload when the store still cannot supply the handle, block the affected action or, if the scope cannot be safely determined, the account’s affected activity-writing entry points. Show “Couldn’t verify whether this activity was saved” and offer to check again. Resume only under the recovered ID. Complete loss of origin storage can destroy local identity and requires recovery outside the normal Retry path.

| Outcome | Evidence and allowed transitions |
|---|---|
| Pending | A durable matching outbox record exists and no terminal outcome is established. It may proceed through the shared gate or stay paused offline. Pending can become unknown, confirmed, definitively failed or discarded as evidence changes. |
| Unknown | Dispatch or storage may have committed and the evidence is missing, contradictory or unreadable. Retain identity and copies. A positively matched outbox read, server receipt, definitive failure or durable discard can resolve it. A stale GET, expired claim, abort or missing active copy cannot reset it to idle or authorize a fresh-ID Retry. |
| Validated success | A matching server receipt from the shared decoder or a correctly bound persisted receipt. Later stale responses or read errors cannot overturn the server fact. Persist the receipt and remove only matching copies in one transaction. On uncertain local commit, retain the handle and reconcile the receipt before any further cleanup. |
| Definitive failure | A proven pre-dispatch failure with no possible earlier send, or authoritative evidence that this exact operation failed without committing. A later refusal alone cannot disprove an earlier ambiguous send. Preserve retryable work under the same ID and require authoritative reconciliation for contradictory terminal evidence. |
| Durable discard | A committed, account-bound decision for the identified operation fences further dispatch across formats. A possible or confirmed prior server send remains a separate fact. Claim cleanup, abort and lost transaction acknowledgements cannot by themselves establish discard or server cancellation. Resolve ambiguous acknowledgements by rereading the decision, otherwise report uncertainty. |
| Physical state after discard | Preserve F2/F3. Report **removed** only when the final scan verifies absence, **known remaining** for an observed copy, and **unverified** when opacity or a failed read prevents proving absence and no survivor was found. Opaque bytes stay preserved. A verified final scan supersedes an earlier cleanup error for reporting, while retaining the diagnostic. Report each logical activity once, with prior-send information, and keep unidentified storage distinct. The result is bounded to that observation. |

`activitySync` owns network proof and same-operation retry. `offlineHabitQueue` owns identity binding, claims, atomic settlement, durable discard and physical verification. Home, Timeline and sign-out consume outcomes. A client-side display projection never settles, discards or forgets an operation.

## Options and proposed scope

| Option | Correctness, compatibility and release implications |
|---|---|
| A. Patch each failing branch | Small diffs and no migration. Separate direct, replay, marker and Home fixes leave independent decisions about success and retries. Exact witnesses can pass while offline, cross-tab or account transitions still diverge. High risk of another ordering-specific correction. |
| B. Consolidate the client contract | Reuses the outbox, account lease, claim and discard machinery. Introduces a shared receipt and outcome type and an ID-keyed UI projection. Keep active and retired readers and use additive versioned fields in existing records. No database or IndexedDB schema migration planned. Preserve legacy fences and gate uncertain old markers. Moderate UI and race-regression scope, bounded by matching receipts, exact representations and two-tab tests. Older mixed writers and rollback builds remain release controls. |
| C. Add a server contract | An authenticated exact-ID read would improve lookup coverage. Current persisted intent and idempotency satisfy the demonstrated failure cases. |
