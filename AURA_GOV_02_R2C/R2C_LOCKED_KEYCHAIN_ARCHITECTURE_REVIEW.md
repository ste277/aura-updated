# R2C: Dedicated Locked-Keychain Architecture Review (Phase E)

**Reviewed:** `AURA_GOV_02_R2B/R2B_LOCKED_KEYCHAIN_DESIGN.md` (R2B manifest-verified).
**Proposal:**
- a dedicated keychain `~/Library/Keychains/aura-rot.keychain-db` with its own password, **not** in the search list;
- `-l` and a timeout longer than the run;
- items with `-T ''`;
- unlock via a tty prompt, `lock-keychain` in `finalize`.

**Outcome: REQUIRES DESIGN CHANGES.** The direction is sound. The changes come in two tiers:
- **Tier 1, design-only (apply in the prototype harness before it runs):** D-A1, D-C1, D-C2, D-D1–D4, D-G1.
- **Tier 2, must be measured by the prototype:**
  - D-B1 (lock-state probe), D-B2 (ACL choice), D-B3 (kill and relock, plus a watchdog);
  - locked-state reads and dumps;
  - `-l` sleep lock;
  - an isolated Always Allow on a throwaway keychain with automation confirmed OFF;
  - password-prompt behaviour while locked.
- **The prototype may proceed once Tier 1 is applied. Production adoption requires every D-* item closed.**

## A. Keychain isolation
- **Separate keychain:** it removes exposure to the always-unlocked login keychain (silent overwrite/delete K4/K5 while unlocked), and to Keychain Access.app browsing by default.
- **Explicit targeting:** every call must pass the file path; this is proven feasible (R2B, R2B-6).
- **Search list and default:** the R2B/R2B-6 guards show the pattern. Measured: `create-keychain` doesn't add the file to the search list.
- **Required change D-A1:** the launcher must **refuse** if the dedicated keychain appears in the search list or is the default (detects tampering via Keychain Access.app).

## B. Lock lifecycle

| Stage | Status | Gap or required change |
|---|---|---|
| Initial locked state | **Unverifiable today:** no side-effect-free CLI query of lock state was established | **D-B1 (P1):** define and test a lock-state probe, e.g. `show-keychain-info` behaviour when locked. Without one, "relocked" can't be evidenced |
| Explicit unlock | tty prompt (`unlock-keychain <path>`, no `-p`) | the password is typed into Terminal (keystroke exposure to same-user processes and keyloggers); see D |
| Authorized operation | with `-T ''`, **each observed read raised a dialog asking for the keychain password** (property 8: owner-reported, n=1, unlocked) | **D-B2 (P1):** decide between **(i) `-T ''` + lock**: 2 password-entry dialogs per rotation, which trains the owner to type the keychain password into GUI dialogs (phishing surface), and **(ii) a default ACL (trust `security`) + lock**: no item dialogs, but **silent reads by any same-user process during the unlock window**. Neither is free; the choice must be explicit and tested. **Out-of-scope alternatives:** a dedicated signed helper as the only trusted app (instead of `/usr/bin/security`), or external or hardware-backed custody |
| Immediate relock | `lock-keychain` in `finalize` | **D-B3 (P1):** SIGKILL, crash or power loss skip `finalize`, so the keychain stays unlocked until timeout or sleep. **Require:** a short run, the shortest feasible `-t`, an **independent relock watchdog** (a one-shot `lock-keychain` after N minutes, detached from the launcher), and an independent post-run lock check (D-B1) |
| Timeout | `-t` > max run time | conflicts with D-B3; see the trade-off |
| Sleep and wake | `-l` locks on sleep | **UNVERIFIED** on this Mac |
| Crash and interruption | trap-based relock only | as D-B3 |
| Restart and recovery | after reboot the keychain is locked (expected) | **UNVERIFIED**; low risk |

## C. Authorization and ACLs
- **Restricted ACL and one-time Allow:** established (properties 1–2, 6).
- **Persistent trust:** an Always Allow on the dedicated keychain persists in its ACL. Expected (**UNVERIFIED**) to give silent reads **only while unlocked**.
- **Required change D-C1:** a **pre-flight ACL check with identity**. Refuse if the decrypt entry isn't `applications (0)` (the parser with requirement lines from R2B-6 exists).
- **Required change D-C2:** a post-run ACL check, where `OPEN` means STOP, re-create the item and re-rotate (the remediation is already documented).
- **`/usr/bin/security` trust:** any trust given to it applies to **every** same-user caller. **Unacceptable for the production item, unless D-B2 selects option (ii) with an explicit, recorded owner acceptance** of silent same-user reads during the unlock window.

## D. Credential custody

| Aspect | Assessment | Required change |
|---|---|---|
| Keychain password generation | not specified | **D-D1:** ≥ 128-bit random, generated by the password manager |
| Storage and retrieval | "in the password manager" → **copy/paste puts it on the clipboard** (the R0 class of exposure again) or manual typing of a long random string | **D-D2 (P1):** a custody procedure without the clipboard (manual entry of a typeable high-entropy passphrase, or password-manager auto-type), with clipboard managers and Handoff off; or explicitly accept clipboard exposure for the **keychain** password, which protects the DB credential |
| Circularity | the DB credential is protected by the keychain password, which lives in the password manager. The password manager becomes the root of trust; no circularity **if** the password manager doesn't depend on this keychain | **D-D3:** record the dependency chain explicitly |
| Recovery | lost keychain password means the DB credential is lost. **Acceptable**: recovery = a fresh rotation (role unused until Phase C) | document as the recovery path |
| Rotation of the keychain password | `set-keychain-password` (interactive) | **UNVERIFIED** procedure |
| No plaintext in scripts, logs, argv, env | the launcher pattern is proven: stdin-only secret, validated tty input, no FIFO | keep; add the R2B-6 input hardening (EOF, IFS, type-ahead) to the launcher (RK-14) |
| Offline copies | the keychain file is in Time Machine; anyone with the file and password decrypts offline | **D-D4:** strong password; decide on backup exclusion |

## E. Process boundaries
- **Concurrent reads:** each is gated (R2B-6). Child processes and shells inherit nothing secret (stdin pipe design).
- **Same-user processes:** can raise genuine dialogs or unlock prompts (phishing), and can delete or replace the keychain **file** (availability; detectable by validation).
- **Privileged administrator:** not defended (file + password offline; process inspection).
- **Automation with Accessibility:** may act on dialogs. Procedural control only (keep it OFF; preflight check). **Not technically enforced.**

## F. Operational reliability

| Failure | Behaviour required |
|---|---|
| Failed unlock | STOP; nothing sent; keychain stays locked |
| Failed or denied read | STOP; the in-memory value is used for ALTER (never a keychain read); the PENDING/LIVE semantics are unchanged |
| Crash or interrupt | relock in a trap; post-run lock check (D-B1); `validate_pending` recovery as today |
| Locked at startup | expected state; required |
| Keychain missing or replaced | STOP; recovery = re-create + re-rotate (no secret recovery from an untrusted file) |

## G. Auditability
- **Today:** script logs only (sanitized; proven redaction).
- **Gaps:**
  - no OS-level audit of keychain access attempts;
  - lock/unlock events not evidenced (D-B1);
  - attacker-initiated dialogs are invisible to the log.
- **D-G1 (P2):** log the script's own sha256, ACL plus identity before and after, lock-probe results, `mdat` of the items, and the macOS version.
- **D-G2 (P3, optional):** evaluate `log show --predicate 'process == "securityd"'` for access events. **UNVERIFIED**; it may need admin rights.

## Verdict
**REQUIRES DESIGN CHANGES:** D-A1, D-B1, D-B2, D-B3, D-C1, D-C2, D-D1–D4, D-G1.

The dedicated locked keychain **materially improves**:
- at-rest integrity (writes need the password);
- the at-rest confidentiality bar;
- the blast radius of a mistaken Always Allow (expected to be limited to unlock windows, UNVERIFIED).

Note: "writes need the keychain password while locked" is **partly established** (reviewer, throwaway; property 9a).

It **doesn't** solve:
- user-mediated approval risk;
- indistinguishable or concurrent dialogs;
- automation, or a compromised or privileged local actor.
